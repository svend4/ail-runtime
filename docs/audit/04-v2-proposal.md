# 04 — Собственный вариант: AIL Runtime v2

Реализация: `mvp/src/v2/` (12 модулей, 55 тестов). Демонстрация: `cargo run --bin v2-demo`. Формальное описание: `docs/v2/specification-v0.2.md`. Ниже — обоснование решений, формулы и предложения, выходящие за рамки реализованного.

## 0. Принципы v2

1. **Вычислять, а не декларировать — на всех уровнях.** Рёбра, конфликты, контракты, антиподы, риск — всё выводится из кода и геометрии. Декларации допускаются только как *приоры* с явным весом.
2. **Монотонность и границы доказываются тестами.** Каждая метрика имеет свойства, зафиксированные в `#[test]`.
3. **Библиотека молчит и не паникует.** Все диагностики — значения (`SwapReport`, `Report`, `Refinement`); все ошибки — `Result`.
4. **Идентичность содержимого ≠ идентичность истории.** Content-hash и chain-id — разные вещи.
5. **Обязательство — тоже результат анализа.** Что нельзя доказать статически, становится проверяемым условием вызова, а не умолчанием.

## 1. Архитектура

## 2. Модель насыщенности v2

Для ребра `e = (u,v)` три компоненты в `[0,1]`:

```text
topology(u,v) = J_w(u,v) · (1 − exp(−C_w(u,v) / support_scale))
   J_w  = Σ_x min(w(u,x), w(v,x)) / Σ_x max(w(u,x), w(v,x)),  x ∈ (N(u)∖{v}) ∪ (N(v)∖{u})
   C_w  = Σ_x min(w(u,x), w(v,x))                              (взвешенные общие соседи)
usage(e)   = 1 − exp(−max(w_e − 1, 0) / usage_scale)          (феромон; вес 1 = нейтрально)
prior(e)   = приор символа из алфавита                         (декларированное знание)

saturation(e) = 1 − (1 − topology)(1 − usage)(1 − prior)       (noisy-OR)
degree(e)     = D1 если s < 0.25; D2 если s < 0.75; иначе D3
```

**Свойства (все в тестах `v2::relation::tests`):**

| Свойство | Тест |
|----------|------|
| `reinforce` никогда не понижает насыщенность ребра | `reinforce_never_lowers_saturation` |
| декларированный `✕` — D3 без контекста; `—` без контекста — D1 | `declared_conflict_is_d3_even_without_context` |
| топология растёт с размером клики и ограничена 1; K₃, K₄ — D2, K₅⁺ — D3 (без приора) | `topology_grows_with_clique_size_and_is_bounded` |
| ⬡-узел модуля не раздувает топологию внутренних рёбер | `module_node_does_not_inflate_topology` |
| неизвестный узел/ребро, петля, дубликат, запрещённый kind → `Err` | `errors_instead_of_panics` |

Сравнение на одном графе (треугольник, затем `reinforce(a,b,+5)`):

| | до | после |
|--|----|-------|
| v1 | 0.500 (D2) | **0.143 (D1)** |
| v2 | 0.393 (D2) | **0.885 (D3)** |

Почему noisy-OR, а не сумма/среднее: любая *сильная* компонента должна насыщать ребро (декларированный конфликт — конфликт, даже в разреженном графе), все слабые — давать низкое значение; при этом монотонность по каждой компоненте гарантирована.

## 3. Контракты и refinement

Контракт функции — её символьные эффекты (`symbolic::effects_in`), не зависящие от нумерации регистров (тест `register_renaming_does_not_change_effects`):

```text
Transfer:
  reads  : p0.f0, p1.f0
  writes : p0.f0 := (p0.f0 - p2);  p1.f0 := (p1.f0 + p2)
  guards : (p0.f0 >= p2)
  ret    : true
  typed  : reads {(Wallet,balance)}, writes {(Wallet,balance)}
```

Правила сравнения `new` против `old` (`contract::check_refinement`):

| Событие | Класс | Основание |
|---------|-------|-----------|
| функция удалена; арность/тип параметра изменились | **violation** | ломает вызывающих |
| guard исчез | **violation** | «ослабление» в терминах проекта |
| новая запись в поле | **violation** | расширение побочных эффектов |
| guard добавлен | change (semantic) | дуализм Лисков: усиление предусловия |
| изменилось записываемое выражение / возврат | change (semantic) | меняет пост-состояние |
| новое чтение | change (semantic) | расширение предусловия существования поля |
| изменился набор вызовов; добавлена функция | change (structural) | не меняет наблюдаемых эффектов |

**Инлайнинг чистых вызовов.** `assert CheckBalance(w, a)` и `assert w.balance >= a` — один и тот же guard: если callee чист (нет записей), его возвращаемое выражение подставляется (`symbolic::inline_pure_calls`, глубина 8). Поэтому делегирование guard-а — refinement, а не нарушение (тест `delegating_the_guard_to_a_pure_call_is_a_refinement`).

## 4. Ownership: статика + обязательства + runtime

`ownership::analyze` доказывает для прямолинейного тела: нет чтения неинициализированного, нет use-after-move/consume, нет двойного потребления, индексы в пределах файла регистров, возврат живого значения, `Return` присутствует, код после него недостижим; предупреждает о мёртвых записях.

Что не доказуемо статически — различность двух изменяемых объектов одного типа — становится **обязательством** `DistinctMutableParams{a,b}`. `vm::Vm` проверяет его при каждом вызове:

```text
Transfer(x, x, 300) → Err(AliasedUniqueParams { func: "Transfer", a: 0, b: 1, object: ObjectId(1) })
```

Тест `without_the_check_the_documented_order_mints_money` воспроизводит исходную уязвимость (1000 → 1300) на VM без обязательств — чтобы регрессия была видимой.

## 5. Граф, выведенный из кода

`derive::derive` по типизированным футпринтам:

| пересечение f и g | ребро |
|-------------------|-------|
| обе пишут (type, field) | `✕` Conflict / Ownership, вес = число полей |
| одна пишет, другая читает | `▲` Unique / Ownership, направление writer → reader |
| обе только читают | `□̸` Shared / Ownership |
| f вызывает g | `→` Directed / Control |
| модуль ∋ f | `⬡` Hyper / HyperMember |

Результат для `PaymentsModule` (ни одна связь не декларирована):

```text
Transfer ✕ Refund          sat=0.909 D3
Transfer ▲ CheckBalance    sat=0.697 D2
Refund   ▲ CheckBalance    sat=0.697 D2
PaymentsModule # Transfer Refund CheckBalance
```

Это ровно та картина, которую `commerce_graph.md` и `m2m_glyph_line.md` рисовали вручную.

## 6. Пайплайн hot-swap v2

```text
propose(new):
  1. refinement = check_refinement(old, new)
  2. ownership  = analyze(f) для каждой f ∈ new
  3. touched    = функции с семантическими изменениями/нарушениями
     affected   = рёбра текущего (выведенного) графа, инцидентные touched (без ⬡)
     risk       = max по affected: D1→Medium, D2→High, D3→Critical;
                  нет touched: структурные изменения→Medium, иначе Low
  4. decision   = Reject(нарушения | ошибки ownership | Critical при политике)
                | AcceptWithWarnings(High/Critical без reject)
                | Accept
commit(new, report): history ← old; module ← new; граф пере-выводится;
                     health-снимок; lineage.append (Merkle)
```

Демонстрация (`v2-demo` §5–§8): удаление guard-а → Reject по контракту **и** Critical по связности; «комиссия» (контракт цел, выражение изменилось) → Critical на ребре `✕`, Reject при строгой политике, AcceptWithWarnings при мягкой; делегирование guard-а чистой функции → Medium, Accept; no-op → Accept, Low, новое поколение с тем же content-hash и другим id.

## 7. GERMES: вычисленная геометрия

`germes::hexagon_cyclic()` даёт истинный порядок `+--, ++-, -+-, -++, --+, +-+` (шаг 60°, веса чередуются 1,2,1,2,1,2), антиподы — на 180°. Исправленная таблица антиподов для доменов v0.1:

| Домен | Вершина | Антипод | Домен-антипод |
|-------|---------|---------|---------------|
| Devices | `--+` | `++-` | Analytics |
| Payments | `-+-` | `+-+` | Content |
| Users | `+--` | `-++` | Logistics |

Тест `documented_antipode_table_has_two_errors` намеренно фиксирует расхождение с документом: если документ исправят, тест нужно обновить.

**Предложение.** Нумеровать домены по циклическому порядку, а символ домена выводить из его положения: вершины веса 1 (треугольник «пробуждения») получают направленные/порождающие символы (`→ △ ∠`), веса 2 («консолидации») — устойчивые (`◇ □̸ —`); центр — `✕`. Тогда «характер» связи между доменами определяется их угловым расстоянием: 60° — соседство (`—`), 120° — треугольник (`◇`/`△`), 180° — антипод (`✕`).

## 8. Алфавит и M2M

Единая таблица (`alphabet::TABLE`) — 10 строк: символ, имя, Unicode, клавиша, приор, направленность, допустимые kinds. Предложенные клавиши для отсутствующих глифов: `.`→`·`, `>`→`→`, `!`→`▲`. `%` — модификатор «принудительно D3», `$` — команда, не ребро.

Грамматика M2M (реализована, round-trip проверен):

```ebnf
line     := empty | comment | relation | hyper | command
relation := IDENT GLYPH IDENT { "%" }
hyper    := IDENT "#" IDENT { IDENT }
command  := IDENT { ARG }
GLYPH    := '"' | '.' | '>' | '(' | '*' | "'" | '&' | '!' | ')' | unicode-символ
comment  := "//" …
```

`Lnk a g b` (макрос клавиатуры) разбирается как relation. `RelationGraph::from_m2m` строит граф и возвращает команды (`Bal`, `Rei`, `RAG`…) вызывающему.

## 9. Здоровье графа

- `transitivity = 3·треугольники / wedges` — нормативная «N/D» (глобальный коэффициент кластеризации), ⬡-узлы исключены.
- `Lever` как в v1, но с поправкой: при отсутствии массы D1 и D3 рычаг *не определён*, а не «перекошен».
- Зона — по доминирующей доле D1/D2/D3 среди *отношений* (⬡-рёбра считаются отдельно).

## 10. Lineage

```text
content_hash = SHA256("ail/v2/module\0" ‖ canonical(module))
id           = SHA256("ail/v2/generation\0" ‖ content_hash ‖ "\0" ‖ parent_id ‖ "\0" ‖ generation)
```

`Lineage::verify(modules)` проверяет номера поколений, ссылки на родителя, пересчёт id и соответствие сохранённых модулей хэшам (тест `tampering_is_detected`).

## 11. Что в v2 сознательно не сделано

| Отложено | Причина | Где в дорожной карте |
|----------|---------|----------------------|
| Ветвления/циклы в AST | символьный и ownership-анализ требуют CFG и join-точек; прямолинейный код покрывает все примеры проекта | Фаза 2 |
| Hyper-операции в AST (`Op::Hyper`) | нужны реальные мультиобъектные сценарии; сейчас достаточно ⬡-узла модуля | Фаза 2 |
| Контентные вершины (Entity/Article/Detail) | требуют модели контента; предложение ниже (§12.4) | Фаза 3 |
| VizGraph JSON/HTML | v1 `VizScene` остаётся; v2 даёт данные (`render`, `to_m2m`) | Фаза 3 |
| WASM-мост клавиатуры | после стабилизации API | Фаза 3 |
| Подписи поколений | после появления многоакторного обмена | Фаза 4 |

## 12. Инновационные предложения (за пределами реализованного)

### 12.1 Шардирование из графа конфликтов

«ShardActor» получает смысл: функции, связанные `✕`/`▲`-рёбрами, обязаны исполняться в одном акторе (сериализация доступа к общим полям); компоненты связности ownership-подграфа — минимальные единицы шардирования; функции без ownership-рёбер между компонентами могут исполняться параллельно. Раскраска графа конфликтов даёт верхнюю оценку числа параллельных исполнителей. Это превращает D1/D2/D3 из диагностики в **планировщик**.

### 12.2 Семантический diff как артефакт lineage

`SwapReport` (нарушения, изменения, затронутые рёбра, риск, решение) должен сохраняться в поколении рядом с `reason`. Тогда lineage отвечает не только «что было», но и «почему приняли», а `verify` может проверять, что политика не менялась задним числом.

### 12.3 Обязательства как типы вызова

`DistinctMutableParams` — первый представитель. Следующие: `Owns(p)` (вызывающий передаёт владение), `ReadOnly(p)`, `NoReentry`. Набор обязательств функции — её *capability-сигнатура*; вызов разрешён, если набор вызывающего покрывает набор вызываемого. Это и есть практическая форма `Borrowed/BorrowedMut` без изменения интерпретатора.

### 12.4 Контент как код

Сущность (`Phone-X1`), деталь (`Price`) и статья — объекты с `TypeTag` в той же куче, с теми же полями. Тогда: `Article □̸ Entity` выводится из ссылки статьи на поля сущности; `Detail → Function` — из чтения поля функцией; lineage контента — та же Merkle-цепь. Тезис «код и контент — один граф» перестаёт быть декларацией.

### 12.5 Самокалибровка порогов

Вместо константы «marginality ≈ 0.5» — обучаемые пороги `d2_low/d3_low`: система накапливает статистику «swap на ребре с насыщенностью s привёл к откату/инциденту» и сдвигает пороги так, чтобы доля отказов в D2 оставалась в целевом коридоре. Jamming-метафора становится операционной: критическая точка — та, где частота отказов меняет режим.

### 12.6 M2M как протокол gossip с подписями

Строка M2M + id поколения + подпись = минимальное сообщение между акторами о дельте графа. `from_m2m` уже разбирает; осталось добавить конверт `@gen <id> @sig <…>`.

### 12.7 Спецификация глифов вместо бинарных шрифтов

Хранить глифы Solan как SVG/bitmap-описания в репозитории и собирать TTF скриптом (`fontforge`): воспроизводимо, лицензионно прозрачно, диффуемо.

## 13. Дорожная карта

| Фаза | Цель | Критерий готовности |
|------|------|---------------------|
| **0 — Стабилизация (эта ветка)** | сборка, тесты, CI, v2-ядро | `cargo test` зелёный; `v2-demo` соответствует документам |
| **1 — Миграция** | v1-демо переводятся на v2 API; `IMPLEMENTATION_STATUS` переписывается по фактам | ни одного «✅» без теста |
| **2 — Язык** | `.ail` парсер → `v2::ast`; ветвления; `Op::Hyper`; межпроцедурный ownership | примеры из `examples/*.ail` компилируются и проходят анализ |
| **3 — Граф и UI** | контентные вершины; VizGraph JSON + HTML-просмотр с шрифтом; WASM-мост клавиатуры (`Lnk/Bal/Rei/Swp` исполняются) | клавиатура показывает живой `SwapReport` |
| **4 — Распределение** | шардирование из графа конфликтов; обмен M2M с подписями; lineage с `SwapReport` | два актора синхронизируют граф и поколения |

## 14. Как мигрировать с v1 без удаления

1. Оставить v1-файлы как есть; пометить в `lib.rs` комментарием `// legacy` (аддитивно).
2. Новый код импортирует только `ail_mvp::v2::*`.
3. Когда `main.rs` будет переведён на `v2::vm` (отдельное решение владельца), v1 можно вынести в `legacy/` — это единственный шаг, требующий перемещения.
