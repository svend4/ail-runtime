# 01 — Концептуальный и теоретический аудит

## 1. Замысел проекта (как он читается из документов)

AIL Runtime заявляет себя как **Semantic Layer**, двойственный к «Continuum» (Form Layer): Continuum стабилизирует форму (проекты, файлы, окружение), AIL — смысл (семантику, владение, контракты). Основные идеи:

| Идея | Где описана | Суть |
|------|-------------|------|
| Binary AST | `architecture.md`, `main.rs` | Код — не текст, а граф операций `Op` над регистрами и объектами |
| Ownership | `specification.md` §6, `ownership-analyzer.md` | Один владелец; `Owned / Borrowed / BorrowedMut / Consumed`; конфликт `✕` |
| Hot-swap + lineage | `hot-swap.md` | Замена модуля только без ослабления контрактов; каждое поколение хэшируется и связано с родителем |
| Star Gate | `visual-edges.md` | Алфавит из 8 символов, описывающий *характер* связи |
| GERMES | `germes-mapping.md` | Шесть доменов как проекция куба Q³ вдоль диагонали; центр — совпадение полюсов |
| D1/D2/D3 + насыщенность | `connectivity-degree.md`, `saturation-usage.md` | Вычисляемая мера «открытости/текучести/жёсткости» ребра; D2 — рабочая зона |
| Marginality, Lever | `lever-balance.md`, `steps/*` | Диагностики здоровья графа по аналогии с jamming и теоремой Рамсея |
| Код + контент — один граф | `edge-rules.md`, `commerce_graph.md` | Функции, сущности, статьи и детали — вершины одного графа с типизированными рёбрами |
| M2M-строки, шрифты Solan, клавиатура | `font-stargate-map.md`, `rag-macros.md`, `tools/` | Печатный носитель алфавита; макросы для графа и RAG |

Это цельная и узнаваемая программа: «семантика кода как граф с измеримой связностью, который эволюционирует, не ослабляясь».

## 2. Сильные стороны концепции

1. **Единый алфавит отношений.** Идея описывать и data-flow, и ownership, и конфликты, и группировку одним набором символов — продуктивна: она даёт общий язык для анализатора, визуализации и человека.
2. **Принцип «насыщенность вычисляется, а не декларируется»** (`saturation-usage.md` §8). Это правильная установка: операционные решения (риск swap, строгость borrow) должны опираться на измеримые свойства.
3. **Lineage как первоклассная сущность.** Хэш содержимого, родитель, поколение, происхождение — минимальный, но верный набор для воспроизводимости.
4. **Послойность.** Архитектура в восемь слоёв (`architecture.md`) задаёт понятные границы ответственности.
5. **Двойственность с Continuum.** Разделение «форма/смысл» — хорошая рамка для позиционирования относительно систем сборки и оркестрации.
6. **D2 как целевая зона.** Мысль, что система должна жить не в разреженном и не в жёстком режиме, а в «критическом» — интуитивно сильная и даёт операционную цель для автоматики (reinforce/decay).

## 3. Разрывы между замыслом и реализацией

### 3.1 Граф связей задаётся руками

Принцип «вычислять, а не декларировать» реализован только для *насыщенности*. Сами **рёбра** в v1 вводятся вручную (`link_functions("Transfer","Refund", Conflict, …)`, `build_payments_relation_graph()`). Конфликт `Transfer ✕ Refund` существует лишь потому, что демо его напечатало. Семантический слой, который не выводит отношения из семантики, остаётся аннотационным слоем.

**Корень проблемы:** AST живёт в бинарном крейте (`main.rs`), а граф — в библиотеке; `actor_with_graph.rs` вынужден завести *свой* `BinaryFunction { name }` без тела. Граф физически не может увидеть код.

### 3.2 Ownership: четыре состояния заявлены, одно реализовано

Интерпретатор v1 реализует только линейное потребление регистров (`Move` → `Consumed`). Заимствований (`Borrowed/BorrowedMut`) нет; `ObjectRef` клонируется свободно в `LoadField/StoreField`; аргументы `call()` копируются. Следствие: `Transfer(w, w, amount)` принимается. В компиляции, *документированной* в `examples/compilation.md` и `examples/transfer_refund.md` (обе загрузки до записей), такой вызов создаёт `amount` из ничего (1000 → 1300). Это ровно тот класс ошибок, который ownership-модель обязана исключать (`&mut` + `&mut` на один объект).

`ownership-analyzer.md` описывает статический анализатор, но в коде его нет.

### 3.3 Hot-swap: «ослабление» = «имя пропало»

`hot-swap.md` обещает двухстадийную проверку: структурную и семантическую (`contracts_not_weakened`, ownership, SMT). Реализована только часть первой стадии — существование имён. Нет понятия контракта в коде, поэтому удаление `assert` из `Transfer` при сохранении имени — «совместимое обновление».

Концептуально не обсуждён **дуализм Лисков**: при замене нельзя *усиливать* предусловия (ломаются вызывающие) и нельзя *ослаблять* постусловия/инварианты (ломаются гарантии). `assert` в AIL играет роль guard-а; удаление guard-а — ослабление гарантии, добавление — усиление предусловия. Оба — изменения, но разного класса; документы этого различия не делают.

### 3.4 Насыщенность и шкала D1/D2/D3

- **Анти-монотонность.** Взвешенная формула включает вес самого ребра в знаменатель, но не в числитель. Усиление ребра (pheromone) *понижает* его насыщенность. Документ `step3-weighted-saturation.md` утверждает противоположное («часто используемые связи мигрируют к D3»).
- **Недостижимость D3.** Невзвешенная формула `2|C|/(deg u + deg v)` включает сами `u,v` в степени: для клики Kₙ значение `(n−2)/(n−1)`, то есть D3 (> 0.75) начинается с K₆. Пример в `connectivity-degree.md` («Transfer ✕ Refund, s ≈ 0.9») невозможен ни в одном примерном графе.
- **Символ против вычисления.** Политика «предпочитать вычисленное, символ — лишь метка» делает декларированный `✕` без общих соседей ребром D1, по которому `can_borrow_unique` разрешает уникальное заимствование через конфликт. Декларированное знание (это конфликт!) обнуляется.
- **Marginality.** В документе — «N/D, где N ≈ треугольники, D ≈ степени свободы, критическое значение ≈ 0.5». В коде — доля пар вершин с хотя бы одним общим соседом: для любой клики от K₃ равна 1.0, для демо-графа 0.333. Порог «≈ 0.5» не выведен ни из чего.
- **Теоретические ссылки.** «Parisi–Zamponi 2026», «Bradač / off-diagonal r(s,k)» приводятся без названий, DOI или формулировок. Jamming-теория описывает фазовые переходы в стёклах, теория Рамсея — неизбежность клик/независимых множеств в больших графах; обе используются здесь как *метафоры* для «разреженный / критический / жёсткий». Это допустимо, но должно быть названо метафорой, а не «практическим аналогом интерполирующей функции f(t)». Для 3–6-вершинных графов асимптотические результаты не применимы.

### 3.5 GERMES: геометрия верна, таблица — нет

Проекция куба вдоль пространственной диагонали действительно даёт правильный шестиугольник с двумя полюсами в центре; два треугольника (веса 1 и 2) — корректно. Но антиподы, «перечисленные» в `germes-mapping.md`:

```text
--+ ↔ -++   (неверно: 60°; антипод --+ это ++-)
-+- ↔ +-+   (верно)
+-- ↔ ++-   (неверно: 60°; антипод +-- это -++)
```

Также нумерация доменов 1..6 не соответствует циклическому порядку на шестиугольнике (истинный порядок против часовой: `+--, ++-, -+-, -++, --+, +-+`). Сопоставление доменов вершинам и символам (Devices → `→`, Payments → `◇`, …) не имеет сформулированного критерия — это дизайнерское решение, которое стоит зафиксировать как таковое.

### 3.6 Три алфавита

| Источник | Символы | Расхождения |
|----------|---------|-------------|
| README / specification | 8: `— → △ ◇ □̸ ▲ ✕ ⬡` | — |
| `connectivity.rs::StarGateSymbol` | 10: + `Dot`, `Angle` | два символа без документации в README |
| `font-stargate-map.md` (клавиши) | 9: `" ( ' * & $ ) % #` | `$` — «рычаг», `%` — «плотность», не отношения; нет клавиш для `→` и `▲` |

Единой таблицы «символ ↔ Unicode ↔ клавиша ↔ рекомендованная степень ↔ допустимые EdgeKind» нет; M2M-формат описан, но парсер отсутствует.

### 3.7 Lineage без цепи

`content_hash` считается только по содержимому. Совместимый swap даёт потомка с тем же хэшем, `parent_hash` указывает на идентичную строку (видно в выводе демо v1: `gen 0 … e55418a48857 → gen 1 … e55418a48857`). Нет верификации цепочки; в `actor_with_graph.rs` хэш вообще «`hash-gen-N`».

### 3.8 Заявлено, но не представлено в коде

- Hyper-edges как операции AST (`hyper-edges.md`) — только документ.
- `VertexKind` и матрица допустимых рёбер (`edge-rules.md`) — не реализованы.
- Контентные сущности (Entity, Article, Detail), «код + контент — один граф» — в коде нет ни одной контентной вершины.
- «ShardActor» — без шардирования, сообщений, изоляции; это один интерпретатор с одним модулем.
- Control flow (ветвления, циклы), вызовы между функциями (`Call`) — отсутствуют, поэтому data-flow-рёбра между функциями невозможно вывести даже в принципе.

## 4. Оценка стадии

| Ось | Оценка | Обоснование |
|-----|--------|-------------|
| Концепция | **сформулирована, не формализована** | Идеи ясны и связны; определения (насыщенность, marginality, weakening) неполны или противоречат коду |
| Теория | **метафорическая** | Jamming/Рамсей — источники интуиции, а не теорем, применимых к графам из 3–6 вершин; ссылок нет |
| Реализация | **демонстрационный прототип (pre-MVP)** | Не собирается; ключевые модули не выполнялись; 1 тест; принципиальные компоненты (ownership-анализатор, контракты, вывод рёбер) отсутствуют |
| Инструменты | **макеты** | HTML-клавиатуры не связаны с runtime; шрифты — заглушки |
| Процесс | **начальный** | Один автор, один день, нет CI, нет issue/PR, нет версионирования спецификации |

По шкале технологической готовности: TRL 2–3 (концепция сформулирована, принципиальные элементы продемонстрированы фрагментарно).

## 5. Что должно измениться в концепции (кратко)

1. **Вычислять рёбра, а не только насыщенность.** Конфликт — это пересечение множеств записи; уникальный доступ — запись против чтения; shared — чтение против чтения; вызов — control-ребро. Всё это читается из AST.
2. **Контракт = символьная сигнатура эффектов** функции (чтения, записи с выражениями, guard-ы, вызовы, возврат). «Ослабление» определяется как отношение refinement между сигнатурами, а не как сравнение имён.
3. **Ownership = статический анализ + обязательства.** Что не доказывается статически (различность изменяемых объектов), становится обязательством, проверяемым при вызове.
4. **Монотонная модель насыщенности** из трёх именованных компонент (топология, использование, декларированный приор) с доказанными свойствами.
5. **Геометрия GERMES вычисляется**, таблицы — результат, а не вход.
6. **Один канонический алфавит** и один парсер M2M.
7. **Lineage как Merkle-цепь**: идентичность поколения ≠ идентичность содержимого.
8. **Библиотека не печатает и не паникует**: отчёты и `Result`.

Всё это реализовано в `mvp/src/v2/` и описано в `04-v2-proposal.md` и `docs/v2/specification-v0.2.md`.
